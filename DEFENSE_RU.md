# Защита Assignment 1: Builder Pattern

## Сценарий демонстрации на 60–90 секунд

«Программа строит туристическую поездку пошагово: выбирает направление, число дней, проживание, транспорт и занятия. Для этого используется паттерн Builder.

`TravelBuilder` задаёт общие шаги. `TravelPackageObjectBuilder` создаёт объект `TravelPackage`, а `ItineraryBuilder` формирует текстовый маршрут. `TravelDirector` знает порядок шагов и содержит два готовых сценария: City Break в Праге на три дня и Adventure Trip в Алматы на пять дней. Директор работает с интерфейсом и может применять один сценарий к обоим строителям.

Сначала запускается демонстрация. В выводе можно сравнить объект и текст, полученные из одного рецепта. Затем показано самостоятельное построение через цепочку методов: директор удобен для готовых рецептов, но не обязателен для использования Builder.

Готовый `TravelPackage` неизменяем: его поля нельзя переназначить, а список занятий копируется. Общая проверка данных вынесена в `TravelDraft`. Повторное использование строителя не изменяет уже созданный продукт. Пресеты директора заменяют все пять частей, включая занятия, поэтому данные предыдущего пресета не остаются в следующем.

Так один алгоритм построения поддерживает разные представления результата, а клиентский код остаётся понятным».

Из папки проекта выполнить:

```bash
./run.sh
./test.sh
```

## Роли и решения, которые важно объяснить

| Роль | Где реализована | Ответственность |
|---|---|---|
| Builder | `TravelBuilder.java` | Общий контракт пяти шагов; методы допускают цепочки вызовов. |
| Concrete Builder | `TravelPackageObjectBuilder.java` | Собирает объект поездки. |
| Concrete Builder | `ItineraryBuilder.java` | Собирает текстовый маршрут. |
| Product | `TravelPackage.java` и `String` | Два представления одной конфигурации поездки. |
| Director | `TravelDirector.java` | Применяет готовый рецепт к любому `TravelBuilder`. |
| Внутреннее состояние | `TravelDraft.java` | Хранит выбранные значения и общие правила проверки. |

**Разные типы результата.** `getResult()` находится только в конкретных строителях: один возвращает `TravelPackage`, другой — `String`. Директору результат не нужен: он задаёт только шаги. Общий метод с возвращаемым типом `Object` ослабил бы типизацию и заставил бы клиента проверять тип или выполнять приведение.

**Fluent API и ковариантность.** В интерфейсе шаг возвращает `TravelBuilder`, а реализация возвращает собственный, более конкретный тип. Это допустимый ковариантный возвращаемый тип Java. Поэтому после цепочки вызовов на конкретном строителе остаётся доступен его `getResult()`. Если переменная объявлена как `TravelBuilder`, доступен только контракт интерфейса.

**Неизменяемость.** У продукта поля `final`, нет сеттеров; конструктор имеет package-private доступ. `List.copyOf` фиксирует неизменяемый список занятий, независимый от изменений исходной коллекции. Это поверхностная защитная копия: отдельные элементы не клонируются. Для `String` этого достаточно, поскольку строки неизменяемы; значения используемых enum также неизменяемы. Один лишь `final` у ссылки на обычный `ArrayList` не защитил бы его содержимое. Строитель дополнительно копирует переданный список сразу в `setActivities`.

**Проверки и повторное использование.** `TravelDraft` позволяет двум строителям применять одинаковые ограничения без дублирования. В `getResult()` проверяется непустое направление, минимум один день, выбранные проживание и транспорт, минимум одно непустое занятие. При нарушении выбрасывается `IllegalStateException`. Пробелы по краям строк удаляются при настройке. Каждый setter заменяет соответствующее значение; `setActivities` заменяет весь список. Пресеты назначают все пять параметров. Если при самостоятельном повторном использовании назначить только часть параметров, остальные сохранятся: для независимой настройки с нуля следует создать новый строитель.

**Зависимости и именованные значения.** Директор зависит от `TravelBuilder`, а не от конкретного продукта или формата текста. Это иллюстрирует принцип инверсии зависимостей (DIP): можно добавить новое представление без переписывания рецептов. Проживание и транспорт задаются enum; нижняя граница длительности обозначена константой `MINIMUM_DAYS`. Выбранные направления и длительности — понятные данные пресетов.

## Вероятные вопросы на защите

1. **В чём главное назначение Builder?** Отделить пошаговое построение от представления результата и удобно задавать сложную конфигурацию.

2. **Чем он отличается от Factory?** Factory обычно выбирает или создаёт готовый продукт за один вызов. Builder предоставляет последовательность шагов настройки; эти подходы можно использовать вместе.

3. **Почему не длинный конструктор?** Несколько похожих аргументов легко перепутать, а цепочки перегрузок для разных комбинаций (telescoping constructors) разрастаются. Именованные шаги читаются понятнее. Для простого объекта с двумя обязательными полями обычный конструктор может быть лучше.

4. **Зачем два строителя?** Они показывают центральную идею: те же шаги и тот же рецепт создают разные представления — объект и текст.

5. **Обязателен ли Director?** Нет. Клиент может вызвать шаги напрямую. Директор нужен для повторяемых готовых рецептов.

6. **Почему `getResult()` отсутствует в интерфейсе?** Продукты имеют разные несвязанные типы; директору достаточно общего интерфейса шагов. Конкретный строитель возвращает результат с точным типом.

7. **Изменится ли готовая поездка после изменения строителя?** Нет. Продукт получает значения и защищённый список; последующие настройки строителя не переписывают его поля.

8. **Можно ли вызвать `getResult()` до заполнения данных?** Сборка должна завершиться ошибкой проверки, если обязательные данные отсутствуют. Это предотвращает создание некорректного продукта.

9. **Как добавить ещё один формат результата?** Реализовать пять шагов `TravelBuilder` в новом классе и добавить его типизированный `getResult()`. Существующие рецепты директора смогут использовать новый строитель.

10. **Потокобезопасно ли решение?** Строители содержат изменяемое состояние и не предназначены для совместной настройки из нескольких потоков. Готовый неизменяемый продукт можно безопасно читать при корректной публикации.

## Что открыть при ответах

Файлы реализации находятся в `src/main/java/edu/builder/travel/`.

- `TravelBuilder.java` — пять шагов и fluent-контракт.
- `TravelDirector.java` — одинаковый порядок шагов, два пресета и зависимость от интерфейса.
- Оба конкретных строителя — ковариантные возвращаемые типы и разные `getResult()`.
- `TravelDraft.java` — проверки входных данных и замена списка занятий.
- `TravelPackage.java` — `final`, отсутствие сеттеров и защитная копия списка.
- `Main.java` — оба пресета в двух форматах, самостоятельная fluent-сборка и обработка ошибки.
- `run.sh`, `test.sh` — команды сборки, демонстрации и проверок.
